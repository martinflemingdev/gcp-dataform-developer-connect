# Developer Connect / Dataform POC notes

- **Resource scope:** Developer Connect connections belong to a GCP project and region; there is no folder-level connection. Git repository links are children of the connection and live in that same project and region. Application teams can potentially manage links there through delegated IAM and their own Terraform.
- **Residency-compliant setup:** Use the console's data residency option, which creates an account- or organization-owned GitHub App with regional webhook routing. A personal GitHub account is sufficient for this POC. A customer-managed KMS key is optional. Keep the proxy enabled for the initial POC; the company networking decision remains open (see below).
- **Cross-project consumption proved:** Developer Connect connections and Git repository links are project/region-scoped, but a Dataform repository in another project can reference a central GitRepositoryLink by full resource name. The console picker did not expose this path cleanly, but the API does. In the POC, a Dataform repository in `cdmc-data` was created through Crossplane and points at `projects/axial-life-395119/locations/australia-southeast1/connections/syd-data-res-crossplane/gitRepositoryLinks/martinflemingdev-gcp-dataform-developer-connect-xp`.
- **Cross-project IAM requirement:** When a Dataform repository in project A consumes a Developer Connect Git repository link from platform project Z, the project A Dataform service agent needs Developer Connect access on project Z, because the connection and link resources live there. In the POC, the `cdmc-data` Dataform service agent `service-370318638050@gcp-sa-dataform.iam.gserviceaccount.com` was granted `roles/developerconnect.tokenAccessor` and `roles/developerconnect.gitProxyUser` on platform project `axial-life-395119`.
- **Crossplane/provider IAM requirement:** The Crossplane provider service account also needs permission to create Dataform repositories in each consuming project. For the cross-project POC, `crossplane@axial-life-395119.iam.gserviceaccount.com` needed `roles/dataform.admin` in `cdmc-data`; otherwise repository creation failed with `dataform.repositories.create` denied.
- **Onboarding IAM checklist:** For each consuming project, grant the platform/IaC identity permission to create/manage the Dataform repository in that project, grant the consuming project's default Dataform service agent `roles/developerconnect.tokenAccessor` and `roles/developerconnect.gitProxyUser` on the platform project/link, and separately grant the Dataform execution identity the BigQuery permissions it needs (`roles/bigquery.jobUser` plus dataset/table access as appropriate). Developer Connect IAM only covers Git access; it does not grant BigQuery execution access.
- **Terraform / app reuse:** `github_config` selects predefined Google apps; it does not accept an arbitrary custom app ID/private key. `github_enterprise_config` exposes existing-app credentials. In the POC, a second Crossplane-managed Developer Connect connection reused the same GitHub App ID and installation ID from the console-created app and reached `installationState: COMPLETE`.
- **What remains open:** Ten Dataform projects do not establish a requirement for ten connections, and ten connections do not establish an unavoidable requirement for ten apps. We proved one central connection/link can be consumed from another project and that the same GitHub App can be reused for another connection in this personal GitHub.com POC. We have not proved company policy, production GitHub Enterprise behavior, or whether one shared app is the desired governance model.

- **GitHub App owner:** The owner is the GitHub user or organization that controls the app registration, private keys, client secrets, webhook URL, permissions, and repository installations. The POC app is owned by `@martinflemingdev`; an enterprise implementation should normally be owned by the company's GitHub organization or enterprise platform owner, not a personal account.
- **GitHub App ID:** The numeric app identifier, for example `5062914`. Developer Connect stores this as `githubEnterpriseConfig.appId` and uses it with the app installation/private key flow. It is an identifier, not a secret.
- **Client ID:** The OAuth client identifier, for example `Iv23liUGNVEsJAtopBS`. It identifies the app during OAuth/user authorization flows. It is not a secret by itself, but it should still be treated as application metadata rather than something to rely on for security. [GitHub App credentials](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)
- **Public link:** The app page/install link, for example `https://github.com/apps/syd-data-res`. This is not a secret. It is how users/org admins can find or install the app where they have permission.
- **Client secret:** This is separate from the private key. GitHub uses client secrets for OAuth authorization-code flows that produce user access tokens and refresh tokens. Developer Connect/Dataform machine Git access is based on the GitHub App installation/private key path, not a personal access token. Do not expose full client secrets; rotate them if a full value is leaked. A masked tail like `*****84cb1a47` is not the secret. [GitHub client secrets](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)
- **Private key:** This is the GitHub App server-to-server credential. GitHub says the private key signs a JWT used to request installation access tokens. It is different from the OAuth client secret and must be stored as a secret. Developer Connect stored the POC private key in Secret Manager and the connection references it as `privateKeySecretVersion`. If the PEM/private key leaks, rotate it. [GitHub private keys](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps)
- **Private key SHA/fingerprint:** The SHA-256 value shown in GitHub is a fingerprint of the key pair, used to verify that a local private key matches the public key GitHub stores. GitHub documents this verification use. Displaying the fingerprint is not equivalent to leaking the private key and does not let someone reconstruct the private key. It is still operational metadata, so redact it from public/customer-facing docs if there is no reason to show it. [GitHub private key fingerprints](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps)
- **Webhook active/URL/secret:** `Active` means GitHub sends event payloads to the configured webhook URL. In this POC the URL is a Google Developer Connect endpoint. The webhook secret is a separate shared secret used by the receiver to verify GitHub's payload signatures; it is not the client secret and not the private key. Developer Connect stored the POC webhook secret in Secret Manager and the connection references it as `webhookSecretSecretVersion`. Do not expose the webhook secret; rotate it if leaked. [GitHub webhook validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)
- **SSL verification:** Keep SSL verification enabled. It makes GitHub verify the webhook endpoint's TLS certificate when delivering events. Disabling it is not recommended and should not be part of the enterprise design.
- **Redirect URI, setup URL, and redirect-on-update:** These are part of the GitHub App installation/OAuth/control-plane flow back to Google Cloud console/Developer Connect. They are not Git clone URLs. They help Google complete app installation and connection setup after GitHub redirects the user back to Google.
- **GitHub App IP allow list:** The app-level IP allow list is for organizations that choose to inherit allowed IPs from installed GitHub Apps. The POC app currently has no app IP allow list entries. This does not solve the Dataform/Developer Connect egress allowlisting question; that still depends on direct Dataform egress versus Developer Connect proxy/private networking.

- **What the connection region stores:** Developer Connect stores resource data in regional Spanner instances. Connection/link metadata includes app and installation identifiers, credential references, proxy settings, installation state, repository URLs, and link identifiers. With the GitHub data residency option enabled, webhook payloads are queued regionally rather than routed through the default global Pub/Sub path. Selecting Sydney therefore concerns the integration metadata and event queue. [Google residency documentation](https://docs.cloud.google.com/developer-connect/docs/data-residency)
- **What “regional webhook” means:** GitHub sends event notifications to Google's configured receiver; the region concerns Google's handling and storage of those notifications. It does not assign a GCP region to the GitHub App or repository. Webhook notifications are separate from Git clone/pull/push requests. [Webhook handling](https://docs.cloud.google.com/developer-connect/docs/data-residency), [Git proxy](https://docs.cloud.google.com/developer-connect/docs/configure-git-proxy)
- **Dataform and BigQuery locations are separate:** A Sydney connection can serve a Dataform repository in another region; Google notes possible cross-region transfer charges with the proxy. Dataform's repository storage region can also differ from its BigQuery execution location. The execution location (`defaultLocation`) must match the relevant BigQuery datasets. Connection residency does not force those resources into Sydney or establish their compliance with company policy. [Connection locations](https://docs.cloud.google.com/dataform/docs/connect-repository), [Dataform workflow settings](https://docs.cloud.google.com/dataform/docs/manage-repository)
- **Credentials have their own storage configuration:** Authentication secrets are stored in Secret Manager and referenced by the connection. Check the secrets' location/replication configuration separately; do not assume selecting Sydney for the connection places every secret in Sydney. [Connection credential fields](https://docs.cloud.google.com/developer-connect/docs/api/reference/rest/v1/projects.locations.connections), [Secret replication](https://docs.cloud.google.com/secret-manager/docs/choosing-replication)

- **Proxy enabled:** Git traffic follows Dataform → Developer Connect proxy → GitHub. The caller uses Google IAM authentication to the proxy, which issues Git requests on its behalf. GitHub-facing network controls must allow the Developer Connect path; do not assume Dataform's published egress ranges also describe proxy egress. [Proxy documentation](https://docs.cloud.google.com/developer-connect/docs/configure-git-proxy)
- **Proxy disabled:** For a publicly reachable Git host, Dataform can use Developer Connect credentials and connect to GitHub directly. Google permits disabling the proxy for public hosts. The proxy setting is separate from the data residency/app-ownership setting. [Dataform connection requirements](https://docs.cloud.google.com/dataform/docs/connect-repository)
- **Allowlisting depends on the network path:** If proxy is disabled, the Git host sees direct Dataform egress, so allowlisting maps to Dataform regional egress IP ranges. If proxy is enabled, the Git host sees the Developer Connect proxy/private-connectivity path instead; do not assume the Dataform IP table applies. Google does not publish a simple Developer Connect public proxy egress IP table in the proxy docs. For private GitHub Enterprise or on-prem hosts, Google documents the Developer Connect + Service Directory path; for hybrid hosts outside Google Cloud, Service Directory uses `35.199.192.0/19`, which must be routed/allowed. [Dataform egress IPs](https://docs.cloud.google.com/dataform/docs/locations), [GitHub Enterprise private network setup](https://docs.cloud.google.com/developer-connect/docs/connect-github-enterprise-private)
- **Company IP allowlisting:** Google publishes Dataform egress IP ranges by Dataform repository region. These are relevant to direct outbound Git access—not the BigQuery dataset region. The ranges are shared by Google Cloud customers and can change, so use the current official table. This explains the company's request for specific Dataform IPs, but does not establish which networking path they have selected. [Dataform locations and egress IPs](https://docs.cloud.google.com/dataform/docs/locations)
- **Private repositories versus private networks:** A private repository on a public GitHub endpoint still has publicly reachable networking. A GitHub Enterprise server reachable only through private IPs is different: Dataform cannot connect directly to those IPs, and its Developer Connect integration requires the proxy plus appropriate private-network configuration. Allowlisting public Dataform IPs alone does not provide private-network reachability. [Public/private connectivity requirements](https://docs.cloud.google.com/dataform/docs/connect-repository)
- **Company decision to capture:** Confirm whether GitHub Enterprise is public with an IP allowlist or private-network-only. Then document the selected Git traffic path and its actual source IPs/network configuration. Do not finalize a Dataform-IP-only allowlist while assuming the Developer Connect proxy is enabled.
